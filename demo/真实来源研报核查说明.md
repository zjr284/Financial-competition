# 真实来源与自编草稿的 C 核查

此入口服务于开发验收和录屏准备：使用 B 已移交的真实披露与复核事实，核查自编草稿中的数字、单位、期间和口径。草稿可故意注入错误，必须标明“自编测试草稿”，不能当作第三方研报或独立留出集。

## 运行

使用已恢复内容寻址文件、含 `metadata.sqlite3`、`blobs/` 与 `reviewed_facts.json` 的私有来源库。先固定 Git 提交，再执行：

```powershell
python -m demo.verify_draft `
  --source-store PRIVATE_SOURCE_STORE `
  --draft PRIVATE_SELF_AUTHORED_DRAFT.pdf `
  --company SIX_DIGIT_CODE `
  --source SOURCE_DOCUMENT_ID `
  --source SECOND_SOURCE_DOCUMENT_ID `
  --dataset REAL_SOURCE_INJECTED_DEVELOPMENT_ID `
  --output var/NEW_C_REVIEW
```

`--source` 可重复，至少提供一份独立来源。合成资料必须额外加 `--synthetic`。工具只把数据集登记为 development，不提供改成 holdout 的参数。它不校验事实的金融真实性，也不自动识别是否合成，使用者须如实声明资料性质。

工具通过只读 SQLite 连接的 backup 生成独立数据库，复制文件快照与事实清单；新草稿、Run、计算和事件只写输出目录中的 `runtime/`。不复制历史运行目录，故副本仅用于这次新建运行，不用于读取旧 Run 结果。来源文档的原字节与登记 SHA-256 在运行前核对；输出目录必须全新且在来源库之外，失败产物保留以便排查，不覆盖旧结果。

显式使用离线规则适配器与 rules 提取，不因环境变量中配置了云端服务而调用模型。读取完整财报的证据与记录事件可能耗时数分钟；此过程没有省略证据访问日志。TXT 草稿的解析置信度通常不足自动核查阈值，可使用带可解析文本层的自编 PDF；不能为了通过而提升置信度。

## 输出与人工步骤

- `research_verification-result.json`、`report_quality-result.json`：符合公共 TaskResult 的两项实际结果。
- 对应 `*-run.json`、`*-exports/`：Run 版本及 JSON、CSV、HTML 导出。质量分只是规则分，不是人工评级。
- 对应 `*-replay.json`：本次新 Run 的输入、结果、内容和调用轨迹重放对比，不宣称已验证缺少快照的旧云端 Run。
- `annotation-a-blank.json`、`annotation-b-blank.json`：相同结果哈希、原句与来源引用，两份标签/身份/依据均为空，不含系统判定或建议。
- `summary.json`：提交与工作区是否有未提交改动、资料性质、草稿哈希及新 Run 列表；`human_gold_complete=false`、`holdout_metrics=null`。

两位成员独立查看原件填写各自模板，有分歧时第三位裁决；不得共享已填答案或用 AI 代签。按 `eval/标注规范.md` 合并后，该开发案例仍是 development。真正的留出集须另选未参与规则开发的公司并冻结资料和标注，不能把本次已知注入位置的草稿换个 split 当作留出集。

后续反馈及修改意见统一写在对应 PR 的评论或 Review 中，不再另制反馈 ZIP。原件和完整模型响应等私有材料仍保存在私有目录，不粘贴到公开 PR；人工填好的私有模板也不提交 Git。
